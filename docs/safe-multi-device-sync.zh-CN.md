## 当前实现状态

当前代码已实现本次自用范围内的安全修订同步、设备角色与手动权威覆盖：

- 插件设置新增默认关闭的 `safeRevisionSyncEnabled`；用户确认后才启动 capability 检查和 bootstrap。
- 服务端只在 `user-database.type=postgres` 且当前用户的 SQLite 导入校验记录为 `VERIFIED` 时返回 capability；SQLite 用户库和未验证 schema 始终为 unsupported。
- 主数据库可以继续使用 SQLite；Note/File/Folder/Vault、安全同步表和操作日志统一位于 PostgreSQL 的 `user_<uid>` schema，并由同一事务分配 Resource/Vault Revision。
- STRICT/BOOTSTRAPPING Vault 的旧 WebSocket、REST、MCP 和回收站恢复写入口统一在 service 边界 fail-closed；当前 Git sync 只从数据库导出到工作区，不反向写 Vault。
- 文件内容先写持久卷 staging，再记录 `PREPARED` 并执行原子替换。服务启动会枚举用户恢复所有 `PREPARED`；下一次安全资源访问也会先恢复当前 Vault。
- 恢复时若目标 hash 已匹配，则只提交一次资源状态、事件、Vault Revision 和 `COMMITTED` 结果；若替换未完成，则恢复 old-image、移除未完成记录并允许同一 operationId 重新提交。未 `COMMITTED` 的操作不会 ACK 或广播。
- 客户端 baseline/pending 按 `serverFingerprint + uid + vaultId` 双写持久化；远端事件按 Vault Revision 串行应用，分页中断后从持久化 Revision 重新拉取。
- 远端删除只有在本地无 pending、存在已确认基准且当前 hash 匹配时才执行；写入恢复区失败会阻止删除和基准推进。
- 每台设备可选择双向端、本地发布端或远端镜像端。本地发布端通过 2 分钟心跳租约阻止其他设备安全写入；远端镜像端的上传在服务端被拒绝。
- 插件可手动执行“本地覆盖远端”或“远端覆盖本地”，执行前展示 CREATE / UPDATE / DELETE / REPLACE 差异。计划 10 分钟过期；删除或替换达到 50 项或目标清单 10% 时要求输入确认词。
- 权威覆盖在目标端先保存恢复包，默认保留 30 天；执行后重新读取当前远端清单并校验路径、类型、大小和内容 hash。最近一次覆盖可在二次确认后整批恢复并再次校验。
- 执行前会重新校验本地清单，预览后任意本地变化都会让计划失效；服务端进入 `BOOTSTRAPPING` 后会先按当前 Note/File/Folder 记录校准安全元数据，再生成固定远端清单，并在提交前重新校准和比较清单摘要。Note 的哈希与 UTF-8 字节数直接按实际正文重算，不信任迁移或普通同步遗留的 `content_hash/size`，避免把旧的 `size=0` 误报成“预览后变化”。
- 权威覆盖在提交安全基准前发生目标备份、计划过期、角色限制或内容漂移错误时，插件会取消服务端 bootstrap 并清空活动预览；只有已经进入 `STRICT` 后的执行错误才保留恢复包和回滚入口。
- 中文笔记使用与 JavaScript `charCodeAt` 一致的 UTF-16 哈希，超过 10 MB 的附件统一采样开头、中间和结尾各 5 MB；服务端会验证笔记和附件的正文、大小及哈希一致性。
- Obsidian 在覆盖过程中退出时，状态为 `APPLYING` 的恢复包仍可通过“恢复最近一次权威覆盖”继续回滚；嵌套目录按子项到父目录顺序恢复。
- “安全多端同步”旁的问号说明修订保护、三种角色、两个覆盖方向、恢复包和 `.obsidian` 边界。设备角色会锁定有冲突的旧“只读同步”与“离线删除上传”开关。

## 一、目标

为 Fast Note Sync 增加可恢复、可审计、能正确处理离线并发的多端同步能力，覆盖以下三类需求：

- 日常双向同步：Windows 与 Android 均可编辑，连接正常时修改应及时传播
- 连续单向同步：可把设备设为“本地发布端”或“远端镜像端”
- 手动权威覆盖：可明确执行“本地覆盖远端”或“远端覆盖本地”

成功不只意味着两端最终内容相同，还必须保证：

- 旧设备不能用过期状态删除另一设备的新内容
- 误删、错误覆盖和批量镜像均有恢复路径
- 同步中断、重试和重复消息不会产生额外破坏
- 用户能在执行前看到差异，在执行后看到完整报告
- 旧版客户端与新版服务端之间有明确、可验证的兼容策略

## 二、用户场景

### 当前场景

- Windows 是主要编辑端，负责新增、修改、移动、重命名和删除
- Android 当前主要查看，未来可能参与编辑
- 服务端部署在远程 Dokploy，负责协调和保存数据
- 用户希望近期以 Windows 整理后的 Vault 为准，清理远端和手机上的旧路径、旧目录和旧文件

### 目标场景

- Windows 编辑后，Android 在联网时自动收到新版本
- Android 编辑后，Windows 在联网时自动收到新版本
- 两端顺序编辑同一文件时，后续版本自然传播
- 两端离线并发编辑同一文件时，不按设备时钟静默覆盖，而是合并或保留冲突副本
- 任一端误删后，删除可以及时同步，但文件仍可从回收站、历史或事务快照恢复
- 初始化新设备、清理旧设备、迁移 Vault 或灾难恢复时，可显式选择权威数据源

## 三、实现前基线事实

以下结论来自第一阶段改造前两个仓库的代码和测试，用于解释本功能为什么需要新增协议；当前分支的新增行为以上方“当前第一阶段实现状态”为准：

- 当前完整同步是双向差异汇聚，远端独有文件会下发，本地独有文件会上传，结果趋向并集而非单端镜像
- 笔记修改请求已有 `baseHash`，可以识别部分正文修改冲突
- `NoteDeleteRequest` 与 `FileDeleteRequest` 只包含路径、路径哈希和上下文，没有 `baseHash`、预期修订号或操作 ID
- 服务端收到删除请求后会直接软删除并广播；完整同步中的离线删除也缺少版本前置条件
- 客户端收到 `NoteSyncDelete` 或 `FileSyncDelete` 后，会直接调用 `vault.delete`
- 客户端应用远端删除前不会检查本地是否存在待上传修改，也不会验证本地内容是否仍等于最后同步版本
- 当前冲突决策仍大量依赖 `mtime`；设备时钟偏差、复制和恢复操作都可能让 `mtime` 失真
- 只读同步能阻止本地上传，但不会把设备强制整理成远端精确副本
- 服务端已有软删除、笔记历史、ZIP 备份、Git 自动化和多种备份存储，可复用但不能替代同步事务保护
- 默认软删除保留期为 90 天，笔记历史默认保留 100 个版本，历史保存延迟默认为 10 秒

因此，直接增加“按最新时间覆盖”或“强制同步”按钮会放大已有删除风险，必须先补齐协议级并发控制。

## 四、同类工具的可借鉴机制

### Syncthing

- 交换文件索引和内容块哈希，不把文件时间作为唯一事实
- 使用文件版本信息识别顺序修改和并发修改
- 删除通过墓碑传播，冲突时保留冲突副本
- 可配置文件版本控制，用于保留被替换或删除的旧版本

### Obsidian LiveSync 与 CouchDB

- 通过 CouchDB 修订信息和变更流传播更新
- 同一基准上的顺序修改可正常推进，不同基准的修改形成修订冲突
- 数据库保存同步状态，不等同于普通 Markdown 文件夹镜像
- 冲突需要显式解决，不能仅依赖客户端文件时间

### Resilio Sync

- 使用文件索引和分块校验减少重复传输
- 删除和旧版本可以进入 Archive，避免立即物理丢失
- 适合实时文件同步，但安全性依赖版本历史与归档设置

### 本项目采用的原则

- 采用：内容哈希、基准修订、墓碑、冲突副本、版本历史、预演和事务快照
- 不采用：把 `mtime` 作为唯一冲突裁决依据
- 不采用：把“日常双向编辑”和“灾难恢复覆盖”合并成同一个模式
- 不照搬完整向量时钟：本项目已有中心服务端，可用服务端单调修订号以更低复杂度实现等价的并发检测

## 五、核心设计决策

### 5.1 日常同步以修订为准

每个远端资源维护单调递增的 `revision`，每个 Vault 维护用于增量事件流的 `vaultRevision`。客户端保存自己最后确认的资源修订，并在修改、删除和重命名时提交 `baseRevision`。

服务端处理规则：

- `baseRevision == currentRevision`：这是同一条版本链上的顺序修改，可以接受
- `baseRevision < currentRevision`：客户端基于旧版本操作，必须进入冲突处理
- `baseRevision` 缺失且远端已存在：视为未知基准，不允许静默覆盖或删除
- 内容哈希相同：允许幂等确认，不重复创建版本
- `mtime`：只用于展示、兼容旧协议和辅助排序，不用于单独决定胜者

在中心服务端架构下，这比“所有设备都以本地为权威”更安全。Windows 和 Android 都可使用普通双向模式；只有恢复或初始化时才选择权威覆盖。

### 5.2 删除是一个有版本的状态

删除必须生成墓碑修订，而不是仅表达“路径不存在”。墓碑至少保存：

- 资源标识与路径
- 删除前的内容哈希和修订号
- 墓碑修订号
- 操作设备、操作 ID 和服务端时间
- 可恢复内容或对应历史/备份引用

### 5.3 权威覆盖使用两阶段协议

权威覆盖不得复用现有“完整同步”。必须拆成：

```text
MirrorPlan -> 只扫描和生成差异计划
MirrorApply -> 校验计划仍有效后执行
```

`MirrorPlan` 不得产生文件修改。`MirrorApply` 必须绑定计划 ID、源端清单摘要和过期时间，防止用户确认后数据已经变化。

### 5.4 自动单向角色与手动覆盖分离

- 设备角色决定日常持续同步方向
- 手动权威覆盖用于初始化、清理和恢复
- 普通双向设备不设置永久权威端
- Android 开始编辑后，应切回双向模式，而不是与 Windows 同时成为“本地发布端”

## 六、功能需求

## 6.1 协议修订与幂等性

### 服务端要求

- 为笔记、附件和文件夹提供可比较的资源修订号
- 为 Vault 提供单调递增事件修订号，替代仅靠毫秒时间戳的增量游标
- 修改、删除和重命名均校验 `baseRevision`
- 每次客户端写操作携带全局唯一 `operationId` 和稳定 `deviceId`
- 同一 `operationId` 重试必须返回第一次执行结果，不得重复修改、删除或生成历史
- 成功响应和广播消息必须返回新资源修订号与 Vault 事件修订号
- 内容哈希继续用于完整性校验，不替代修订号

### 插件端要求

- 在本机持久化 `path -> revision/contentHash` 的已确认同步基准
- 本地修改、删除和重命名只基于已确认基准发送
- ACK 到达后再推进本地基准；连接中断时保留待确认操作
- 收到重复事件时按修订号幂等忽略
- 本地缓存丢失时进入“未知基准”状态并重新扫描，不得把缺失直接解释为删除

### 建议协议字段

```text
MutationRequest:
  deviceId
  operationId
  baseRevision
  baseHash
  expectedPathState

MutationResult:
  resourceRevision
  vaultRevision
  contentHash
  conflictType
```

## 6.2 安全的日常双向同步

- 默认模式保持“双向可写”，不改变现有用户的同步方向
- WebSocket 连接正常时，小于 1 MB 的笔记修改应在 5 秒内开始传播
- 同一基准上的顺序修改直接产生下一修订
- 不同基准上的并发修改不得用 `mtime` 静默覆盖
- Markdown 可以复用现有合并能力做三方合并；无法无冲突合并时保留冲突副本并通知用户
- 二进制附件不做正文合并；冲突时保留两个版本并提供选择
- 服务端事件顺序、客户端应用顺序和 ACK 必须可追踪
- 设备时钟相差数小时不得改变冲突判定结果

用户所需的“Windows 改后自动覆盖 Android、Android 改后自动覆盖 Windows”由这一模式实现，但准确名称应是“最新已确认修订传播”，不是“最新时间戳强制覆盖”。

## 6.3 删除与重命名安全

### 本地发起删除

- 插件发送删除前读取最后确认的 `baseRevision` 和 `baseHash`
- 服务端仅在当前修订等于基准修订时接受删除
- 若远端已有更新，返回“删除与修改冲突”，不得删除或广播删除
- 接受删除后生成墓碑、历史记录和可恢复事件

### 客户端接收删除

- 本地内容仍等于最后确认哈希且无待上传操作时，才允许应用删除
- 本地内容不同、存在待上传修改或基准未知时，生成“删除与修改冲突”
- 应用删除前把本地内容放入插件恢复区或可靠回收站，不得直接不可恢复删除
- 删除事件成功应用后才更新本地修订基准

### 重命名与移动

- 重命名必须包含旧路径的预期修订，以及新路径“应不存在”或预期修订条件
- 服务端应把重命名作为单个可审计操作处理
- 如果无法做到数据库原子重命名，必须以同一事务 ID 执行“新路径写入并校验成功，再为旧路径创建墓碑”
- 目标路径已被另一设备创建时必须冲突，不得覆盖
- 文件夹移动必须覆盖内部笔记、附件和空目录的完整结果

## 6.4 手动权威覆盖

插件设置或命令面板增加两个明确命令：

- `立即以本地覆盖远端`
- `立即以远端覆盖本地`

### 本地覆盖远端

- 本地有、远端无：上传
- 两端都有且内容不同：以本地覆盖远端，不做正文合并
- 本地无、远端有：在远端创建墓碑并进入回收站
- 本地已移动或重命名：创建新路径并删除远端旧路径
- 最终选定同步范围内的远端清单、内容哈希和目录结构应与本地一致

### 远端覆盖本地

- 远端有、本地无：下载
- 两端都有且内容不同：以远端覆盖本地，不做正文合并
- 远端无、本地有：把本地文件移动到恢复区
- 远端已移动或重命名：创建新路径并清理本地旧路径
- 最终选定同步范围内的本地清单、内容哈希和目录结构应与远端一致

### 预演要求

执行前必须列出：

- 新增
- 覆盖
- 删除
- 重命名或移动
- 冲突
- 排除项
- 因大小限制、读取失败、权限或哈希失败而跳过的项目

扫描不完整时 `MirrorPlan` 必须标记为不可执行。被排除或跳过的资源不能被解释为“源端不存在”。

### 执行要求

- 计划默认 10 分钟后过期
- 执行前重新校验源端清单摘要和目标端当前修订
- 修改远端前强制下载并验证将被覆盖或删除的远端原像，不能只依赖延迟历史
- 修改本地前强制保存将被覆盖或删除的本地原像
- 顺序必须是“保存目标原像 -> 校验计划修订 -> 按依赖顺序写入或删除 -> 重新读取两端清单并校验哈希”
- 支持中断、重试、幂等和失败恢复
- 完成后生成事务报告，并支持按事务回滚

### 批量删除保护

- 任何手动镜像都必须确认
- 删除数量达到 50 个或达到选定范围 10% 时，进入高风险确认
- 高风险确认必须显示新增、覆盖、删除总数，并要求输入本地化确认词（简体中文为“确认覆盖”）
- 自动模式命中高风险阈值时只能暂停，不能自动放行
- 阈值应可配置，但不得允许完全关闭事务快照和修订校验

## 6.5 连续单向同步与设备角色

每台设备提供以下角色，设置只保存在本机，不参与 Obsidian 配置同步：

### 双向可写

- 默认角色
- 本地和远端的已确认新修订双向传播
- 并发修改进入合并或冲突流程

### 本地发布端

- 本地新增、修改、删除持续发布到远端
- 远端出现非本设备产生的新修订时暂停发布并告警，不得用本地静默覆盖
- 同一 Vault 同时最多存在一个有效本地发布端租约
- 适合阶段性使用 Windows 作为唯一编辑端
- Android 需要编辑前必须先退出远端镜像角色，并确保 Vault 不处于单一发布端锁定状态

### 远端镜像端

- 只接收远端修订，不上传本地编辑
- 初次启用时必须执行一次“远端覆盖本地”的预演和确认
- 本地孤立旧文件进入恢复区后清理，使设备成为远端精确副本
- 若用户仍在本地改动文件，插件必须保留本地原像并提示该改动不会上传
- 适合当前主要用于查看的 Android 设备

### 角色管理

- 服务端记录设备 ID、设备名称、插件版本、协议能力、角色和最后在线时间
- 本地发布端使用带过期时间的服务端租约，设备长期离线后不能永久锁死 Vault
- 检测到多个发布端、旧版可写客户端或角色冲突时，暂停破坏性操作
- 角色变化必须进入同步日志

## 6.6 备份、恢复与版本历史

- 同步不等于独立备份，文档与 UI 必须明确区分
- 继续保留服务端软删除和历史版本能力
- 镜像事务必须创建独立的立即快照，默认至少保留 30 天
- 客户端为被覆盖或删除的本地原像创建事务恢复包，默认至少保留 30 天
- 客户端恢复目录必须排除在同步扫描之外，避免恢复包再次被同步
- 用户可以从插件查看镜像事务，执行整批回滚或恢复单个路径
- 恢复操作本身要生成新修订并传播，不能直接篡改历史
- 备份失败、空间不足或恢复区不可写时，禁止执行权威覆盖
- 应建议用户另行配置定时 ZIP、Git、S3、R2、WebDAV 或本地离线备份

## 6.7 设置与交互

插件端新增“同步方向”设置：

- 双向可写
- 本地发布端
- 远端镜像端

新增“权威覆盖”操作区：

- 以本地覆盖远端
- 以远端覆盖本地
- 查看上次计划或事务报告
- 查看可恢复事务

交互要求：

- 当前角色和同步方向必须在设置页与状态栏清晰显示
- 权威覆盖按钮不得放在普通“立即同步”旁边造成误触
- 点击后先扫描并展示差异，用户确认后才执行
- 扫描、备份、传输、校验、删除和完成阶段分别显示进度
- 失败时显示可执行的恢复或重试动作，不只显示通用错误
- 只读/镜像状态下的本地编辑要给出明确通知

服务端 Web UI 要能查看：

- 设备及协议能力
- 当前本地发布端租约
- 镜像计划和事务历史
- 墓碑、冲突和恢复状态
- 每次事务的新增、覆盖、删除、跳过和失败清单

## 6.8 范围和排除规则

首个可用版本覆盖：

- Markdown 笔记
- 普通附件
- 文件夹与空目录

首个可用版本不覆盖：

- `.obsidian` 配置镜像
- 多个本地发布端自动选主
- 仅凭文件名猜测重命名
- 跨 Vault 镜像
- 用 `mtime` 自动解决并发冲突

排除目录、扩展名、附件大小限制和云预览规则必须在计划与执行阶段使用同一套过滤器。任何过滤或读取失败都不能触发对应路径删除。

## 6.9 权限与安全

- 权威镜像必须要求同时具备选定范围的读取和写入权限，只读令牌不得创建可执行计划
- 建议增加独立的 `vault_mirror` 权限；若复用现有权限，也必须在服务端集中校验笔记、附件和文件夹的组合权限
- `deviceId` 只用于识别设备和幂等，不能替代用户身份、令牌权限或服务端租约校验
- `MirrorPlan` 只能返回调用者有权查看的路径和统计信息
- `MirrorApply`、回滚、发布端租约解除和高风险删除都必须写入审计日志
- 日志不得记录令牌、备份密码或文件正文；路径日志沿用现有用户隔离边界
- 事务快照和本地恢复包必须继承现有存储访问控制；启用备份加密时不得降级为明文快照
- 计划 ID、事务 ID 和操作 ID 必须使用不可预测值，并校验用户、Vault、方向和过期时间绑定关系

## 6.10 性能与可靠性

- 已连接设备之间，小于 1 MB 的笔记修改应在 5 秒内开始传播
- 清单和差异必须分批或流式处理，不得把所有附件正文同时放入服务端或移动端内存
- 以 20,000 个资源的测试 Vault 为基准，`MirrorPlan` 必须完成且不能导致 Obsidian 无响应或 Android 进程因内存不足退出
- 客户端连续占用 UI 线程超过 100 毫秒的扫描工作必须主动让出执行权，并保持可取消
- 服务端必须对计划、事务和分片传输设置并发上限、背压和超时
- 网络中断后只能从已确认检查点恢复；未收到 ACK 的操作不得被本地标记为完成
- 计划执行期间服务端重启后，事务必须可恢复为“继续、回滚或明确失败”之一，不能停留在未知状态
- 性能验收必须记录 Windows 与至少一台代表性 Android 设备的资源数量、总大小、耗时和峰值内存

## 七、协议兼容与迁移

- WebSocket 握手增加能力协商，例如 `resourceRevisionV2`、`mirrorPlanV1`、`deviceRoleV1`
- 新字段使用向后兼容的 protobuf 字段号，禁止重用已有字段号
- 新版服务端在功能未启用时保持当前默认双向行为
- 权威镜像和设备角色只对支持相应能力的插件开放
- Vault 开启严格修订保护后，旧客户端的删除和重命名请求必须被拒绝并返回升级提示
- 旧客户端缺少 `baseRevision` 的修改请求只能进入兼容或冲突流程，不得覆盖严格模式下的新修订
- 升级过程要为现有资源回填初始修订，并验证墓碑与历史数据可访问
- 数据库迁移必须可重复执行，失败后可安全重试
- PostgreSQL 的每个 per-user schema 必须持久化唯一的 SQLite 导入验证记录；普通建表/回填不得伪造 VERIFIED，只有全表导入和校验在同一事务提交后才允许 capability
- 回滚到旧服务端前必须明确说明新修订字段和事务记录的兼容影响

- Go 遵循现有 domain/service/DAO 分层，协议校验不得只放在路由层

type SyncRole = "bidirectional" | "local-publisher" | "remote-mirror";

- 某项需求只有在插件端、服务端和对应测试全部完成后才能标记为已交付

## 十二、验收标准

- 顺序编辑在双向模式下自动传播，不依赖设备时间判断胜者
- 并发编辑不会静默丢失任一端内容
- 过期客户端的删除请求不能删除较新远端修订
- 远端删除不能直接删除存在未提交修改的本地文件
- 两个权威覆盖方向都先生成完整、可复核的差异计划
- 扫描不完整、备份失败或目标状态变化时，镜像执行被阻止
- 镜像被中断后可安全重试，不重复删除或重复生成版本
- 权威覆盖完成后，选定范围的路径清单和内容哈希与源端一致
- 远端镜像端可以清理本地孤立旧文件，并能从恢复区找回
- 本地发布端冲突或租约异常时暂停，而不是静默覆盖其他设备写入
- 每次删除、覆盖、镜像和回滚都有设备、时间、路径、旧修订和新修订记录
- 所有新增自动化测试通过，且不得新增未说明的现有测试回归

### 第二阶段：手动权威覆盖

### 自用 PostgreSQL 迁移命令

迁移镜像必须以只读方式挂载现有 `/fast-note-sync/storage` 与 `/fast-note-sync/config`，并通过环境变量提供 PostgreSQL 目标连接。命令默认只盘点 SQLite 源数据并检查 PostgreSQL 可连接性，不创建 schema 或目标表：

```bash
fast-note-sync-service safe-sync-import --config config/config.yaml
```

核对每个 UID 和每张表的源计数、最大主键与摘要后，再显式执行导入：

```bash
fast-note-sync-service safe-sync-import --config config/config.yaml --apply
```

可用 `--uid 1,2` 限定用户，或用 `--source-path` 指定旧 SQLite 主文件基准路径。任一表的源/目标计数、最大主键或关键字段摘要不一致时，整个用户导入事务回滚，不写 `VERIFIED`，也不得切换生产服务。

## 十七、已确认决策

以下默认值已用于当前实现：

- 日常默认策略：双向修订同步，不使用最新 `mtime` 强制覆盖
- 当前 Windows：默认保持双向可写；整理远端前可手动执行一次“本地覆盖远端”
- 当前 Android：后续手工导入时建议设为远端镜像端；需要编辑时再切换为双向端
- 手动镜像计划有效期：10 分钟
- 高风险删除阈值：50 个或选定范围的 10%
- 镜像事务快照和本地恢复包默认保留：30 天
- 首版范围：笔记、附件和文件夹，不含 `.obsidian` 配置
